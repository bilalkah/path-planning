01

How each planner searches

Grid planners search cell by cell. Tree planners sample free space and join points with straight segments.

planning/grid_base

Grid search: one loop, three containers.

Every free cell is a node. Its neighbours are the 4 or 8 adjacent cells (search_space), and every move costs 1, diagonals included. A*, BFS and DFS run the same loop: take the next node, skip it if it was already visited, log it, mark it visited and push its free neighbours with the current node as their parent.

The container that holds the frontier is the only real difference. It decides which node comes out next, and that decides how much of the map gets explored and what the path looks like.

grid · std::queue

Breadth-first search

Takes the oldest node in the queue, so the search spreads out in rings: every cell one move from the start, then every cell two moves away, until the goal reaches the front.

Path
Fewest moves. With every move costing 1, the first time the goal comes out of the queue no shorter path exists.
Cost
Expands every cell closer to the start than the goal, in every direction.
bfs.cpp ↗
grid · std::stack

Depth-first search

Takes the newest node on the stack, so it commits to one direction until it is blocked, then backs up to the most recent unexplored branch. The path is the chain of parents that led there.

Path
Finds one if it exists, but a winding one. On large maps it can be tens of thousands of moves long.
Cost
Unpredictable: it can stumble on the goal early or sweep most of the map first.
dfs.cpp ↗
grid · std::priority_queue

A*

Takes the node with the lowest f. g counts the moves from the start; h is the straight-line distance to the goal. The weight blends them:

f = (1 − w) · g + w · h

heuristic_weight is 0.7 in config/grid_base.yaml, so the search leans toward the goal. 0 orders by g alone, like BFS; 1 is greedy best-first.

Path
Short, not guaranteed shortest: h can overestimate when a diagonal move costs 1, and w = 0.7 weights it further.
Cost
Usually a fraction of the cells BFS expands.
astar.cpp ↗
planning/tree_base

Sampling: grow a tree through free space.

RRT and RRT* never walk the grid. Each iteration picks a random free cell, finds a tree node to grow from, and steps toward the sample by at most max_branch_length cells. Steps shorter than min_branch_length are dropped.

Before a step joins the tree, Get2DRayBetweenNodes lists every cell on the straight line between the two points. One occupied cell rejects the step. Paths come out as straight segments at any angle, not moves between neighbouring cells.

tree · rapidly-exploring random tree

RRT

Grows from the tree node nearest to each random sample. Samples land mostly in large unexplored regions, so the tree reaches into open space quickly. It stops as soon as a new node lands within goal_radius of the goal.

Path
The first one found. Every edge points at a random sample, so it zigzags.
Cost
Stops early. Each iteration scans the whole tree for the nearest node.
rrt.cpp ↗
tree · RRT with rewiring

RRT*

Finds the tree nodes within neighbor_radius of the sample and tries them in order of cost; the new node attaches to the cheapest one it can reach. Then it rewires: a neighbour that is cheaper to reach through the new node moves under it, and IterativelyCostUpdate pushes the change down that subtree. Cost is f = g + h: edges from the root plus Euclidean length.

Path
Keeps getting shorter after the first one is found. It prints each improvement to std::cout; the demo charts them.
Cost
Uses every one of the max_iteration samples.

02

Planners don't draw. They log.

Planning and drawing share one data structure and nothing else.

config/*.yaml Configuration

main.yaml picks the map, planner, start and goal. grid_base.yaml and tree_base.yaml hold the parameters.

main.cpp Planner factory

GetPlanner() builds one planner behind IPlanningWithLogging and calls FindPath(start, goal, map).

utility/i_planning.h The log

Every node in the order the planner logged it, plus the final node. A mutex guards it.

readers Two consumers
tools/visualizerSDL3 thread polls GetLog() every frame
web/planner_bindings.cppthis page replays it after FindPath
01 / interface

One interface, five planners

IPlanning declares FindPath. ILogging adds GetLog and ClearLog. main.cpp picks a planner by planner_name and never needs to know which one it holds.

02 / log

The log is the visualization

Planners append to log_ under a mutex while they search. The visualizer runs on its own thread and redraws whatever the log holds, so the search is visible while it runs and the planner knows nothing about drawing.

03 / paths

Paths are parent chains

Each NodeParent holds its cell, a shared_ptr to its parent and a Cost {g, h, f}. ReconstructPath walks from the final node back to the root. RRT* rewires by moving these pointers.

04 / geometry

Collisions are ray casts

Get2DRayBetweenNodes walks the unit vector between two nodes and lists the cells it crosses. One occupied cell rejects the edge. A unit test pins the ray from (2, 7) to (5, 9) at five cells.

web/

From the C++ to this page.

The demo does not reimplement the planners. It compiles them. Emscripten builds the planning/ libraries unchanged, and a small binding file gives the page two functions.

  1. The EMSCRIPTEN branch of CMakeLists.txt builds the five planner libraries and the bindings. No SDL, no yaml-cpp, no tests.
  2. loadMap writes the .map file into Emscripten's in-memory filesystem, so planning::Map parses it as the native build does.
  3. plan builds the planner with the constructors main.cpp uses, calls FindPath, and returns the path with GetLog(). Lines written to std::cout come along with it.
  4. A Web Worker hosts the module, so a long search never freezes the page. The page draws the log on a canvas.
