How the demo works

        

          Each run sends the map, the points and the parameters to the C++
          planners, compiled to WebAssembly and running in a Web Worker.
          FindPath runs to the end, then the page replays
          GetLog(): the nodes in the order the planner logged
          them, which is what the native SDL3 visualizer draws. For A*, BFS,
          DFS and RRT that is the exact order of the search. RRT* rewires as
          it goes and its log holds only the final tree, so a node that was
          later rewired shows as a dot until its new parent appears. RRT and
          RRT* sample with std::random_device, so every run
          grows a different tree.
        

      

    


    
    

      

        
The planners

        
Two families, five planners.

        
Grid planners search cell by cell. Tree planners sample free space and join points with straight segments.

      


      

        

          planning/grid_base
          
Grid search: one loop, three containers.

          

            Every free cell is a node. Its neighbours are the 4 or 8 adjacent
            cells (search_space), and every move costs 1,
            diagonals included. A*, BFS and DFS run the same loop: take the
            next node, skip it if it was already visited, log it, mark it
            visited and push its free neighbours with the current node as
            their parent.
          

          

            The container that holds the frontier is the only real
            difference. It decides which node comes out next, and that
            decides everything else: how much of the map gets explored and
            what the path looks like.
          

        

        
      


      

        

          
          

            01 · grid · std::queue
            
Breadth-first search

            

              Takes the oldest node in the queue, so the search spreads out in
              rings: every cell one move from the start, then every cell two
              moves away, and so on until the goal reaches the front.
            

            

              
Path
Fewest moves. With every move costing 1, the first time the goal comes out of the queue no shorter path exists.

              
Cost
Expands every cell closer to the start than the goal is, in every direction.

            

            

              bfs.cpp ↗
              
            

          

        


        

          
          

            02 · grid · std::stack
            
Depth-first search

            

              Takes the newest node on the stack, so it commits to one
              direction and keeps going until it is blocked, then backs up to
              the most recent unexplored branch. The path is the chain of
              parents that led there.
            

            

              
Path
Finds one if it exists, but a winding one. On large maps it can be tens of thousands of moves long.

              
Cost
Unpredictable: it can stumble on the goal early or sweep most of the map first.

            

            

              dfs.cpp ↗
              
            

          

        


        

          
          

            03 · grid · std::priority_queue
            
A*

            

              Takes the node with the lowest f. g counts the moves from the
              start; h is the straight-line distance to the goal. The weight
              blends the two:
            

            
f = (1 − w) · g + w · h

            

              With heuristic_weight 0.7 from
              config/grid_base.yaml, the search leans hard toward
              the goal. 0 orders nodes by g alone, like BFS; 1 ignores g and
              becomes greedy best-first search.
            

            

              
Path
Short, but not guaranteed shortest: h can overestimate when a diagonal move costs 1, and w = 0.7 weights it further.

              
Cost
Usually a small fraction of the cells BFS expands.

            

            

              astar.cpp ↗
              
            

          

        

      


      

        

          planning/tree_base
          
Sampling: grow a tree through free space.

          

            RRT and RRT* never walk the grid. Each iteration picks a random
            free cell, finds a tree node to grow from, and steps toward the
            sample by at most max_branch_length cells. Steps
            shorter than min_branch_length are dropped.
          

          

            Before a step joins the tree, Get2DRayBetweenNodes
            lists every cell on the straight line between the two points. One
            occupied cell rejects the step. The result is any-angle paths
            built from straight segments, rather than moves between
            neighbouring cells.
          

        

        
      


      

        

          
          

            04 · tree · rapidly-exploring random tree
            
RRT

            

              Grows from the tree node nearest to each random sample. Random
              samples land mostly in large unexplored regions, so the tree
              reaches into open space quickly. It stops as soon as a new node
              lands within goal_radius of the goal.
            

            

              
Path
The first one found. Every edge points at a random sample, so it zigzags.

              
Cost
Stops early. Each iteration scans the whole tree for the nearest node.

            

            

              rrt.cpp ↗
              
            

          

        


        

          
          

            05 · tree · RRT with rewiring
            
RRT*

            

              Finds the tree nodes within neighbor_radius of the
              sample and tries them in order of cost; the new node attaches to
              the cheapest one it can reach. Then it rewires: a neighbour that
              is cheaper to reach through the new node moves under it, and
              IterativelyCostUpdate pushes the change down that
              subtree. Cost is f = g + h: edges from the root
              plus Euclidean length.
            

            

              
Path
Keeps getting shorter after the first one is found. It prints each improvement to std::cout; the demo charts them.

              
Cost
Uses every one of max_iteration samples.

Inside the C++

        
Planners don't draw. They log.

        
Planning and drawing share one data structure and nothing else.

      


      

        

          config/*.yaml
          Configuration
          
main.yaml picks the map, planner, start and goal. grid_base.yaml and tree_base.yaml hold the parameters.

        

        

          main.cpp
          Planner factory
          
GetPlanner() builds one planner behind IPlanningWithLogging and calls FindPath(start, goal, map).

        

        

          utility/i_planning.h
          The log
          
Every node in the order the planner logged it, plus the final node. A mutex guards it.

        

        

          Readers
          

            
tools/visualizerSDL3 thread polls GetLog() every frame

            
web/planner_bindings.cppthis page replays it after FindPath returns

          

        

      


      

        

          01 / interface
          
One interface, five planners

          
IPlanning declares FindPath. ILogging adds GetLog and ClearLog. main.cpp picks a planner by planner_name and never needs to know which one it holds.

        

        

          02 / log
          
The log is the visualization

          
Planners append to log_ under a mutex while they search. The visualizer runs on its own thread and redraws whatever the log holds, so the search is visible while it runs, and the planner knows nothing about drawing.

        

        

          03 / paths
          
Paths are parent chains

          
Each NodeParent holds its cell, a shared_ptr to its parent and a Cost {g, h, f}. ReconstructPath walks from the final node back to the root. RRT* rewires by moving these pointers.

        

        

          04 / geometry
          
Collisions are ray casts

          
Get2DRayBetweenNodes walks the unit vector between two nodes and lists the cells it crosses. One occupied cell rejects the edge. A unit test pins the ray from (2, 7) to (5, 9) at five cells.

        

      


      

        

          web/
          
From the C++ to this page.

          

            The demo does not reimplement the planners. It compiles them.
            Emscripten builds the planning/ libraries unchanged,
            and a small binding file gives the page two functions.
          

          
    
            
  1. The EMSCRIPTEN branch of CMakeLists.txt builds the five planner libraries and the bindings. No SDL, no yaml-cpp, no tests.
    2. 
            
  2. loadMap writes the .map file into Emscripten's in-memory filesystem, so planning::Map parses it as the native build does.
    3. 
            
  3. plan builds the planner with the constructors main.cpp uses, calls FindPath, and returns the path with GetLog(). Lines written to std::cout come along with it.
    4. 
            
  4. A Web Worker hosts the module, so a long search never freezes the page. The page draws the log on a canvas.
    5.

Benchmark maps

          
Maps from real games.

        

        

          The six maps come from the
          Moving AI Lab 2D pathfinding benchmarks
          (N. Sturtevant, “Benchmarks for Grid-Based Pathfinding”, 2012).
          In the .map format, . and G
          are passable. planning::Map treats every other cell,
          including trees, water and swamp, as occupied.
        

      

    


    

      

        
Open source

        
Run it natively.

        
The native build opens an SDL3 window and draws the log while the planner runs. Choose the map, planner and points in config/main.yaml. A Docker setup is included as well.


git clone --recurse-submodules https://github.com/bilalkah/path-planning.git
cd path-planning
./build.sh       # CMake configure and build
./build/main     # reads config/main.yaml
